## Review

### Correct — what the evidence shows is solid

**Architecture and structure**

- Clean package layout with an explicit dependency rule that is actually honored: `domain` (pure Java, no Spring) ← `app`/`verification` ← `api`/`auth`/`ingestion` ← `persistence`/`config`. I verified there is no `domain` → Spring import and no `features ↔ features` import in the frontend.
- Consistent seam pattern: every service talks to repository *interfaces* (`ShelterRepository`, `UserRepository`, …) with a JPA impl + in-memory fake for unit tests — no service ever touches entities.
- The domain is honest: `User` → `RegisteredUser`/`GuestUser`/`AdminUser` with verification as *claims (data), not subclasses*; `Shelter` carries all lifecycle state as fields with a single documented status writer.

**Security-critical logic verified line by line, all correct**

- `AuthService.login` — Argon2 dummy-hash timing equalizer **plus** the post-verify `user == null` existence guard (the "dummy" password oracle is closed; `AuthService.java:117-138`).
- `JwtTokenService.refresh` — atomic conditional-UPDATE claim (`revoke(hash) == 0` → generic 401) so concurrent double-rotations serialize; `JpaRefreshTokenRepository` stores SHA-256 only.
- `PasswordResetService` — silent no-ops on unknown email/cooldown/day-cap (no enumeration), one active code per user, 5-attempt lockout, reset + mark-used + revoke-all in one `@Transactional`.
- `ContactChangeService.verifyCode` — failed attempts incremented via `@Modifying(clearAutomatically = true)` conditional UPDATE with the domain object kept unmanaged (no stale write-back); failure *returned* so the increment commits.
- `ClientIps` — XFF ignored for untrusted peers, trusted chain peeled right-to-left; unspoofable by construction.
- PII at rest — AES-GCM `v1:` envelopes, domain-separated HMAC blind indexes, `PiiKeys` fails boot on missing/malformed keys, `V13PiiEncryptionMigration` is genuinely idempotent (v1: guard, hash-only backfill, loud collision failure).
- Trust layer — `ShelterReportService` weighted auto-hide tally computed *before* the insert (crossing-trigger only, so a restored/disarmed row never re-hides), dismissed reports excluded in SQL (`SpringDataShelterReportRepository`), auto-confirm only on NEW/USER/by-other-user, duplicate 409 consumes no throttle budget (rollback).
- Ingestion — fetch outside the transaction, single-tx apply, per-source delist with zero-row guard, oversize pre-check, transient-only retries, runaway page cap.
- `LocationResolveService` — entry pinned to `maps.app.goo.gl`, http→https upgrade, userInfo stripped, every hop re-validated (scheme-stable, default port, Google host set), 10 s monotonic budget. No SSRF path.
- Boot guards — `ProdJwtGuard`, `DevEndpointsGuard`, `DevSenderGuard`, `PiiKeys` all fail closed off dev/test via the shared `Profiles.isDevTestOnly` (resolved active set, mixed set not exempt).
- Optimistic locking (B7b) — in-place managed-row mutation preserves `@Version`; commit-time `StaleStateException` is explicitly mapped to 409 (`ApiErrorHandler.transactionSystem` with cycle-safe cause walk).
- `deleteById` calls `flush()` so same-transaction cascade reads are consistent — and the comment explains why.

**Testing** — 130 backend test files including Testcontainers ITs for every concurrency-sensitive seam (`RefreshRotationRaceIT`, `ShelterOptimisticLockingIT`, `PiiAtRestIT`, `ReportThrottleIT`, `UserSuspensionIT`, …) and ~60 frontend spec files. Constraints are pinned by parity tests (`ShelterRequestConstraintParityTest`, `design-tokens.spec.ts`).

### Finding — P2 (report-only; nothing blocks merge/release)

V21 dropped `shelter_reviews`/`review_reports` entirely, and `shelter-detail-page.ts:100` documents "The reviews model is GONE (owner decision)". This is the one user-visible factually-wrong string left. Same staleness in comments: `account-page.ts:27` ("own shelters and reviews in one panel"), `verify-page.ts:111` ("One claim is enough to review/submit"), `admin-gateway.ts:82` ("reviews, reports and occupancy cascade"). Smallest fix: reword the three template lines to "submit shelters and report listed locations" and touch the three comments.

2. **P2 — README (root) materially out of date.** The Features/API sections still describe the removed star-rating review model: the API table lists `GET /account/reviews/mine`, `GET/POST /api/shelters/{id}/reviews`, `PUT/DELETE .../reviews/mine`, `POST .../reviews/{id}/reports` — **none of these endpoints exist anymore** (grep for `reviews` in `src/main/java` returns zero matches). The stack section lists migrations `V1`–`V10` (the repo has V1–V22 + the Java V13), and the test counts ("464 backend / 723 frontend") are stale. The later sections (PII at rest, production deployment, CSV client) *are* current, so the doc is half-accurate — worst of both worlds.

3. **P2 — `frontend/README.md` layout tree is wrong.** It lists `gateways/… review-gateway.ts` (no such file — gateways are account/admin/auth/data-source/geo/geocode/shelter/verify) and `shared/… RatingStars` (zero matches in the codebase); `features/shelter` is described as "detail + reviews (review-form)"; the intro says "the community rating **is** the moderation"; Deferrals still cites `GET /account/reviews/mine` as a shipped M8 endpoint and the M6 journey as "submit shelter → review (star 5)".

4. **P2 — OpenSpec drift.** `openspec/specs/shelter-detail-reviews/` still sits in the *current* specs directory even though the feature was removed by V21, and no change directory (current or `archive/`) documents the removal. `app-polish/spec.md:126-129` and `map-browse/spec.md:53` still pin review/rating behavior. If the specs are the source of truth for this project (the README says so), the removed feature needs its spec archived/replaced.

5. **P2 — Dead seam methods (production-uncalled, test-only).** Each is implemented in both the JPA repo and the in-memory fake and exercised only by ITs:
   - `ShelterRepository.saveAll` (test: `ShelterRepositoryIT`),
   - `ShelterRepository.findAllBySourceIn` (tests only),
   - `ShelterRepository.findActiveBySourceAndReviewStatus` — most misleading: its javadoc says "The admin 'Unconfirmed' queue (community-review-queue v2)", but the admin list is served by `ShelterQueryService.findAllForAdmin` with in-memory filtering; the dedicated queue method has no production caller,
   - `ShelterReportRepository.countByShelterIdAndType` (the weighted tally uses `reportersByShelterIdAndType`; display counts use `countByTypeForShelterIds`),
   - `RefreshTokenRepository.countActiveByUserId` (tests only),
   - `PasswordResetTokenRepository.markUsed` + `findByTokenHash` (the service path is `findActiveByUserId` + `save`),
   - `UserService.getData(User)` (one-line delegation, `UserServiceTest` only).
   Also `RegisteredUser.revoke(VerificationLevel)` is test-only, though its retention is explicitly documented against the Step-1 contract — fine to keep.

6. **P2 — Orphaned javadoc fragment.** `src/main/java/ee/sheltermap/auth/AccountService.java:113` — a stray `/** One batched read of shelter names by id (no N+1; empty map if none). */` sits directly on top of the `deleteAccount` javadoc, evidently a leftover of a deleted method.

7. **P2 — Misplaced JSDoc.** `frontend/src/app/core/models.ts:636-646` — the block describing admin-audit rows ("One row of GET /admin/audit… REVIEW_HIDE/REVIEW_RESTORE values persist…") is attached to the `DataExportShelter` interface instead of the audit contract it describes.

8. **P2 — Clock discipline inconsistencies.** `VerificationClaim.revoke()` (`domain/VerificationClaim.java:76`) and `JpaRefreshTokenRepository.revoke/revokeAllForUser` (`persistence/JpaRefreshTokenRepository.java:48,53`) call `Instant.now()` while the rest of the codebase (including `JwtTokenService`, which sits one call away) takes an injected `Clock`. Tests of those exact paths can't pin the stamp.

9. **P2 — Dismissed-report semantics edge case.** `SpringDataShelterReportRepository.latestByShelterAndUserForShelterIdsAndType` (the `lastVerifiedAt` input, `ShelterQueryService.lastVerifiedFor`) does **not** filter `dismissedAt is null`, while its two sibling queries do. So an admin-dismissed `OPEN_CONFIRMED` report still refreshes the row's "Last verified …" display, contradicting the documented dismissal rule "the report stops influencing anything" (`ShelterReportRepository` javadoc). Impact is display-only, but the asymmetry is unexplained by any comment.

10. **P2 — Contradictory "default" for the registry client.** `application.yml`/`RegistryProperties` default `app.registry.client` to `csv`, while `PaasteametRegistryClient` declares `matchIfMissing = true` (i.e. *it* is the default when the property is absent). The yml always supplies the property so behavior is correct, but the two defaults disagree and the WFS client is documented in the yml as upstream-dead — `matchIfMissing = true` is a misleading vestige.
